# OPL NetFleet 设计白皮书

## 文档定位

本文说明 NetFleet 解决什么问题、为什么采用当前边界，以及理想形态应如何演进。它不定义命令、Schema、阈值或当前设备状态；这些可执行合同唯一归[当前架构](../architecture/overview.md)，当前可用入口归[根目录 README](../../README.md)。两者与本文发生差异时，以当前架构和真实实现为准。

## 摘要

NetFleet 面向 OpenWrt 提供基于微内核的代理与网络管理平台。它把多个机场组织为同一套出口资源，在节点、机场和地区之间取得性能与稳定性的平衡，并在管理服务、代理核心或上游资源失效时让网络退回更低但仍可解释的能力层级。

独立产品与可组合能力是同一方向：策略与机场分离，网络资源与业务能力分离，测量与决策分离，运行选择与历史展示分离，正常运行与灾难恢复分离。Nikki 接入和原生 Mihomo 接入服务于不同使用场景，不定义永久产品身份。微内核组织插件，插件提供订阅、选择、编译、后端和维护能力；未来可沿同一生命周期合同接入其他代理实现。无论使用哪个后端，基础联网和退出能力都应能解除对失败组件的依赖。

## 问题本质

单个机场提供的 Profile 往往同时包含节点、地区组、业务规则、DNS 和展示命名。这种交付方式容易使用，却把五类本应独立变化的事实绑在一起：

- 机场决定有哪些网络资源；
- Profile 作者决定如何分类流量；
- 地区和节点命名决定如何组织出口；
- 客户端决定如何检测健康和切换；
- 用户只能整体接受或整体替换这套设计。

当只有一个机场时，这种耦合尚可接受。接入多个机场后，问题会迅速暴露：同一地区被重复展示，机场之间无法统一比较，某个机场的规则和命名成为全局依赖，AI 等业务资格难以稳定表达，任何一个 Profile 的更新都可能改变整个网络行为。

NetFleet 要解决的不是“再写一套更复杂的 Profile”，而是恢复正确的对象边界：流量分类回答“这是什么流量”，capability 回答“它需要什么出口”，地区和 Provider 回答“有哪些资源”，选择器回答“此刻用哪个资源”，Fail-Open 回答“这一层失败后退到哪里”。

## 设计原则

### 独立产品与可替换实现

OpenWrt 提供基础网络，代理核心负责连接和组内健康检查，NetFleet 组织用户配置、资源、选路和运行维护。产品概念应独立于某个 UI 或代理实现，具体配置、服务及数据面差异由对应后端承担；当前分工见[架构总览](../architecture/overview.md)。

功能替换先证明新实现能完成真实调用、状态回读和故障退出，再切换调用者并删除旧实现。任何阶段都只能有一个订阅事实 owner、一个数据面生命周期 owner 和一个安全退出 owner。插件化改变代码的交付与组合方式，不复制运行状态或控制权。

### 一个事实只有一个 Owner

订阅、配置、测量、选择与历史各有明确 owner。实时健康来自实际运行后端，用户意图来自设备配置，历史用于解释已发生的行为。插件通过版本化接口读取或提交命令，不直接修改其他插件的私有状态；UI 投影也不能反向成为新的事实源。

### 先资格，后性能

速度不能证明业务资格，业务可用也不能证明速度，流量额度更不能由连接失败猜测。候选必须先满足 capability、地区授权、真实叶子、健康和明确配额约束，之后才比较同目标、同轮次的 proxy-path delay。

### 稳定优先于微小收益

节点层应快速避开失活叶子；地区层应保持粘性，只有当前地区失效或替代地区带来明确收益时才切换。这样既避免长期困在明显较慢的地区，也避免轻微网络抖动造成跨地区漂移。

### Fail-Open 是能力降级，不是成功伪装

Fail-Open 的目标是逐级解除对失败组件的依赖。系统可以从优选代理退到其他机场、DIRECT、独立 Recovery Profile，最终由后端清理接管并恢复直通；每一层都必须明确当前还保留什么能力、失去什么能力。

### 配置驱动，但不制造配置系统

机场、地区、capability、门槛和探针应由数据表达，engine 不按名称写分支。配置保持声明式和可审查；插件扩展行为，数据配置选择行为及其参数。新增机场或修改地区映射不应要求开发插件。

### 微内核与插件化能力

微内核保留发现、依赖、服务绑定、调用准入和代码生命周期等组合机制。订阅、选路、
配置编译、代理后端、协议适配、诊断、调度及恢复策略由功能插件提供；没有哪项业务
因为与联网有关就必须固定在内核。系统配置明确选择提供者和必需依赖，插件各自拥有
状态和职责，基础联网与恢复能解除对失败插件的依赖。

Cordis 的上下文、服务依赖和可销毁生命周期为这套组合方式提供参考。设备端使用原生
UCode 服务与进程插件，把这些理念落实到 OpenWrt 的运行模型：组合能力通过公开接口
表达，包管理器负责安装依赖，宿主负责调用依赖与生命周期。当前服务合同见
[微内核与功能插件](../architecture/microkernel.md)，接入与管理面见
[模块与扩展](../architecture/extensions.md)。

任何符合协议的插件都应能独立开发、安装、加载、更新和退出，自有功能和第三方能力
遵循同样的组合规则。热替换围绕接口兼容、依赖解析、在途调用、状态交接和连接排空
设计，资源 owner 明确自己的交接方式。插件来源、发现与分发可以进一步发展为插件
市场，使更多网络能力沿统一开发和安装流程进入产品。

### 跨平台共享业务能力

NetFleet 的长期产品形态包括路由器与桌面客户端。共享业务插件负责订阅语义、策略模型、
规则编译、选路、健康判断和恢复决策；平台插件提供配置存储、凭据、核心进程、网络接管
和软件更新；各端界面调用相同业务服务，并呈现本平台适用的能力。OpenWrt 的路由器管理
界面与 macOS 的桌面窗口、托盘和系统集成可以分别演进。

服务以能力命名，调用者不依赖 UCI、procd、nftables 或某个桌面框架的对象。平台之间应
共享一份业务实现，系统差异由显式绑定的提供者承担。桌面无需复制路由器的 LAN 管理；
每个平台按真实支持的网络接管与恢复能力组合产品，不以空实现伪装功能可用。

UCode 是当前共享服务的运行载体。向 macOS 扩展时，先以同一份源码验证订阅、编译、
Mihomo 启停和自动选择的完整调用链，再决定宿主、权限和分发方式。若调整共享运行时，
迁移目标仍是一份两端共用的业务代码。Clash Verge Rev 可作为桌面交互与系统集成的
参考，NetFleet 的机场、地区、能力和恢复模型保持独立。当前已实现的接口归
[平台能力边界](../architecture/microkernel.md#平台能力边界)。

## 五类网络能力

### 多机场资源整合

NetFleet 把多个订阅的资源编译成统一、可比较、可回退的出口能力。机场提供上游节点，订阅 owner 保存唯一的已验证缓存，策略声明稳定 Provider 身份、地区映射和故障层级。

用户看到的应该是“海外加速”“AI 出口”和多机场地区，而不是某个机场内部结构的简单拼接。新增机场只增加资源数据，不改变选择算法和业务分类。

### 地区、机场和节点的分层选择

三个层级解决不同问题：

- 地区决定延迟级别、内容可用性和连接稳定性，适合带门槛的粘性选择；
- 机场代表相对独立的服务与额度故障域，适合在合格资源中按实时性能竞争，并按显式故障层退回；
- 节点是最细的连接资源，由 Mihomo URLTest 负责快速健康切换。

NetFleet 不使用综合分，也不让长期历史左右当前选择。历史稳定性可以帮助人理解网络，却不应成为不可解释的隐藏权重。当前轮次没有可靠测量时，系统应保持健康路径，而不是制造一个“最佳”。

### 分层 Fail-Open

数据面仍存在时，回退应尽量在运行后端内完成：当前叶子、同地区其他叶子、其他主用机场、显式备用机场、DIRECT。控制面事务失败时恢复完整 Recovery Profile；运行后端无法恢复时，由其数据面 owner 清理接管并进入 passthrough。

这种设计刻意区分三件事：代理链是否可用、数据面是否已经安全退出、关键业务是否可达。三者可能同时成立，也可能只成立其中一部分，系统必须如实报告。

### 面向能力的业务出口

策略不应直接选择机场或节点，而应选择稳定 capability。`standard` 表示常规境外能力，`ai-compatible` 表示满足 AI 地区约束的能力；未来只有出现真实且不同的资格或回退合同时，才应增加新的 capability。

capability 让分类与资源解耦：AI 流量可以跟随海外加速的合规地区，也可以在该地区不合规时独立选择；机场增删、节点改名和地区映射变化不会迫使业务规则跟着重写。

### 安全激活与可观测

网络配置必须可以先生成、后验证、再启用，并且可以随时关闭。编译不改变当前网络；启用和选择必须具备前置身份、运行回读和失败恢复；卸载不能删除仍在使用的路径。

UI 解释当前事实并向 owner 提交命令。用户应能看到当前 capability、地区、机场、叶子、选择原因和 Fail-Open 顺序，也能区分“NetFleet 已启用”“当前走 DIRECT”和“已经退回恢复配置”这些不同状态。

## NetFleet 产品面与可替换后端

用户可以安装完整 NetFleet 产品，也可以从微内核出发按需组合插件。NetFleet 产品面负责首次设置、订阅与机场组织、地区识别、业务出口、自动运行、安全恢复、状态和诊断；设备端唯一配置 owner 把结构化选择转换为可校验 policy。浏览器不直接保存订阅秘密、不生成运行配置，也不实现选择算法。

产品独立包含分发与运行两个层次。版本化 package、LuCI 页面和安装事务提供独立分发；
订阅、代理核心和 OpenWrt 数据面生命周期的统一管理提供运行时独立。两者共同支撑
完整产品体验。当前原生与 Nikki 接入的分工由[架构总览](../architecture/overview.md)维护。

长期运行实现由四个边界组成：

| 边界 | 唯一责任 |
| --- | --- |
| DeviceConfigOwner | 保存结构化产品配置和设备端秘密引用，生成可校验 policy；浏览器不持有订阅 URL/token |
| SubscriptionOwner | 发现、刷新、校验和缓存机场节点源，失败保留上一份已验证内容；同一订阅不能同时由 Nikki 和 NetFleet 写入 |
| RuntimeBackend | 把稳定 capability、机场和地区模型编译到一个代理核心，负责核心启动、重载、停止、controller 回读和延迟测量 |
| OpenWrtDataPlaneOwner | 在同一激活事务中接管或清理 DNS、nft、TProxy/路由，任何失败都能恢复网络直通 |

后端扩展应以完整纵向链为单位：从多个真实实现的配置、服务和数据面差异中提炼稳定
`RuntimeBackend` 接口。未来接入 `native-sing-box` 等后端时，除配置生成外，还应满足
共享 mutation lock、原子启用、owner readback、数据面清理和 Fail-Open 合同。可选模块
的热加载与代理核心的后端替换各有生命周期，两者分别演进。

“支持多个后端”只表示同一时刻可选择一个已验证实现，不表示并行运行多个代理核心、保留双写状态或为最小公分母牺牲安全语义。后端差异留在 adapter，机场、地区、capability、选择理由和用户配置模型保持稳定；某个后端无法提供必需的安全清理或可验证回读时，NetFleet 必须拒绝启用该后端。

后端迁移本身也是一次受保护事务：先在不改变数据面的条件下验证新后端配置和依赖，再建立 DIRECT 护栏，停止旧 owner，启动并探测新 owner；失败时恢复旧 owner，成功并完成 target-local readback 后才提交后端身份。迁移不能同时维持 Nikki 与原生后端双写，也不能把“自动回退到另一个代理核心”变成长期运行模式。

### Zashboard 作为 Mihomo 独立完整运行面

NetFleet 自有页面负责稳定摘要、持久配置和受保护生命周期命令，不应重写 Mihomo 已经成熟的实时连接、流量、内存、规则命中、代理组、Provider 和即时控制体验。对 `native-mihomo` 及仍使用 Mihomo 的过渡后端，Zashboard 是 NetFleet “实时运行”入口打开的独立完整页面；不嵌在 NetFleet 内容区，不增加常驻前端进程或 NetFleet 后台轮询。

完整 Zashboard 是 Mihomo 当前运行态的操作面，不是 NetFleet 的持久配置、订阅或恢复 owner。用户可以在其中进行即时 selector 切换和连接管理；这些操作不会自动写回 NetFleet policy。资源发行、controller 配置和打开入口由所选后端的明确 owner 管理。

“实时运行”只在当前后端能够提供对应运行面时启用。未来其他后端可以提供自己的独立运行面。浏览器认证应在保留完整运行能力的前提下减少凭据传播；当前入口与凭据处理方式由架构文档定义。

## 理想形态：机场无关的策略基线

### 策略来源边界

完整机场 Profile 不应成为长期的策略内容边界。将策略绑定机场交付内容会产生这些结构性问题：

- 更换策略来源可能同时改变规则、DNS、组名和用户操作面；
- NetFleet binding 依赖第三方组名和结构稳定；
- 常规与 AI 等能力受制于机场作者是否提供正确分类；

### 应拆开的两个角色

策略与恢复承担两个独立角色：

**Policy Baseline** 是机场无关的策略来源。它定义有序规则、稳定 capability、必要的本地覆盖，以及与目标网络相关但不属于机场的 Profile 基线。它不包含机场节点，不按机场组名绑定，也不负责订阅下载；其中的 DNS 意图由所选数据面 owner 应用和清理。

**Recovery Profile** 是用户明确选择并独立验证的一份普通后端配置。它在 NetFleet 关闭、事务失败或进程级恢复时提供独立运行路径。它可以来自一个稳定机场，但不参与正常增强拓扑，也不冒充策略来源。

因此，理想链路是：

```text
Policy Baseline + target-local overrides + subscription caches
    -> NetFleet one-shot compiler
    -> enhanced Profile
    -> selected runtime backend and data plane

Recovery Profile
    -> independent native recovery
    -> backend cleanup / passthrough
```

正常运行的策略不依赖任何特定机场；机场只提供网络资源。控制面退出时仍有一份无需 NetFleet 运行即可选择的原生 Profile。两者分离，比“把某个机场 Profile 复制一份作为兜底”更清楚，也不会制造第二份节点事实。

### “自己维护策略”不等于重写规则生态

NetFleet 应拥有策略组合和稳定能力映射，而不是人工维护全互联网域名清单。Mihomo 已原生支持独立的 `rule-providers`、有序 `RULE-SET`、GEOSITE/GEOIP 和本地规则；成熟 OpenWrt 客户端也普遍提供自定义规则、覆写和 rule-provider 管理。

因此 Policy Baseline 最适合由三部分组成，并可保存在一个版本化 bundle 中，而不是拆成三个服务：

1. 少量稳定的顶层规则顺序和 capability 目标；
2. 明确来源的公共 rule-provider 引用；
3. target-local 的精确覆盖，例如必须走某 capability 的私有业务域名。

规则集的下载和缓存交给支持它的运行后端；订阅交给唯一订阅 owner；编译器验证引用并生成最终配置。每项能力可以独立插件化，同一份数据始终由一个服务负责。

策略来源迁移应复用同一编译、选择与激活链，验证规则等价、DNS、关键业务分类、DIRECT
行为及 Recovery Profile 独立性。格式和迁移入口由当前架构维护，不在理念文档中复制。

## 不做什么

NetFleet 的默认产品围绕机场、地区、业务出口、自动选择和安全退出组织。插件生态可以
拓展更多网络能力，内核则保持少量稳定机制。微内核化以独立开发、安装、替换和组合的
实际收益为依据，不按文件数量拆分事务，也不将所有第三方能力都变成默认安装依赖。

项目使用少量稳定概念，持续追求三个结果：更好的出口质量、更小的故障影响面，以及任何时候都能解释并撤销网络接管。

## 调研依据

- [Mihomo Rule Providers](https://wiki.metacubex.one/en/config/rule-providers/)：规则来源可以独立为 `http|file|inline` provider；
- [Mihomo Proxy Providers](https://wiki.metacubex.one/en/config/proxy-providers/)：节点来源、健康检查和过滤是原生对象；
- [Mihomo Routing Rules](https://wiki.metacubex.one/en/config/rules/)：规则按顺序匹配，并可引用 `RULE-SET`；
- [Nikki](https://github.com/nikkinikki-org/OpenWrt-nikki)：负责 OpenWrt 透明代理、Profile/mixin、路由和 nftables 生命周期；
- [MetaCubeX meta-rules-dat](https://github.com/MetaCubeX/meta-rules-dat)：可复用的 Mihomo 规则数据来源；
- [OpenClash](https://github.com/vernesong/OpenClash)：成熟 OpenWrt 客户端对自定义规则、配置覆写和 rule-provider 管理的实践，同时也说明把所有编辑能力塞进运行产品会显著增加复杂度。

这些项目证明了平台原语和可行边界，不构成 NetFleet 的运行依赖。NetFleet 只采用能保持单一 owner、可回退和低复杂度的部分。

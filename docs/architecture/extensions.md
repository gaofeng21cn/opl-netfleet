# 模块与扩展

NetFleet 使用设备端 Extension API v1 组合独立能力。内置模块通过适配器接入，独立插件
通过安装目录动态发现并在独立进程中按调用加载，不需要重启 NetFleet、rpcd 或 Mihomo。
模块注册表负责发现模块、检查接口和
投影组件信息；它不拥有 policy、订阅、测量、选择、证书或网络状态。

## 分工

| 层次 | 责任 | 不承担 |
| --- | --- | --- |
| 核心 | 编译、选优、证据、激活、恢复和共享 mutation lock | 可选增强的私有配置与协议处理 |
| 后端适配 | 唯一启用后端的服务、DNS、透明代理、路由与运行回读 | 第二套业务选择或跨后端双写 |
| 扩展模块 | 限定能力的配置、依赖、生命周期、诊断和局部恢复 | 改写其他模块状态或全局恢复路径 |
| 注册表 | 静态声明、动作路由、API 准入和组件投影 | 自建进程、锁、缓存、下载器或任意执行入口 |
| LuCI / React | 已有页面中的模块状态与受限命令 | 注册代码、解析私有配置、决定运行资格 |

HTTPS 兼容是独立可选软件包；Zashboard 是资源模块，其管理适配器随核心包交付，
面板资源仍独立更新。Nikki 和原生 Mihomo 是互斥后端，不是可同时开关的扩展。
故障恢复、编译和选择当前由内置实现承担。微内核方向下可以沿同一接口逐步插件化，
必需能力由系统配置和依赖关系保证就绪；迁移期间继续保留唯一运行 owner 和可验证恢复。

## Extension API v1

模块在其 application 适配器导出 `extension` 声明，包含 `id`、`label`、`api_version`、
`kind`、软件包、运行依赖、权限类别、UI 插槽与公开动作映射。动作映射只连接既有
CLI/RPC 名称、读写类别和模块内部方法。内置适配器由源码明确导入；独立插件使用下述
固定安装布局和通用调用接口。

`application/extensions.uc` 统一路由已注册动作，`main.uc` 不再逐项列出模块动作。
CLI 名称、rpcd 参数与 ACL 保持不变；声明不会自动扩大 RPC 权限。新增动作必须同时
实现适配器、明确 ACL，并通过声明与真实 RPC/CLI 的一致性验证。模块内部方法仍有
有限白名单，私有备份、tick、排空和引擎启动不能借注册表变成浏览器命令。

独立 HTTPS 包携带 `extension.json`，只声明模块 ID 和实现支持的 API major。
安装版本从 APK 安装记录取得，不用这个接口声明冒充软件版本。缺少或损坏声明、
不支持的 API、缺少运行依赖和不适用后端分别显示，不从安装成功推导运行健康。
依赖清单只投影具名的直接运行工具；虚拟包与传递库依赖由 APK 解析，不把虚拟依赖名
当作实际包名查询。没有安装记录的文件不能冒充已安装软件包。
模块信息复用组件页的一次安装记录读取；不启动 Python、不执行探针、不加载私有 CA，
也不加入常规概览轮询。

不兼容时拒绝新增接管、配置应用与探测。`get` 和 `disable` 是稳定的诊断与退出入口，
不因接口声明损坏被封锁；前者继续返回真实 revision，后者仍由原模块校验 revision、
获取共享锁并执行旁路与排空。关闭不能被注册表伪装成直接杀进程。模块不存在时 get
返回未安装，其余动作明确失败；基础 status、选优、恢复和其他模块仍可用。

接口准入只约束管理动作，不替代 gateway 的连接归属、内核租约或模块运行健康判定。
安装后保持关闭，启用仍需原有显式确认和目标验收。已建立连接不能因插件卸载、升级
或宿主退出而假称无损恢复；HTTPS 排空与故障旁路合同见[HTTPS 兼容](https-compatibility.md)。

## 扩展与交付

新增模块先明确独立 caller、状态、权限、失败影响和可恢复的生命周期，再选择内置适配器
或独立插件交付。仅增加新的机场、地区或业务出口时修改 policy，不创建代码插件。
UI 复用现有配置、组件和诊断插槽，不为每个模块增加顶层页面。

声明、路由、缺失与不兼容场景由源码合同验证；软件包必须携带适配器及接口声明。
涉及文件系统、服务或数据面部署时继续遵守[QEMU 与设备准入](overview.md#准入证据)。
运行依赖由 OpenWrt 软件包管理器管理；核心组件更新与独立插件包操作各自明确目标。
可选包升级与卸载继续经过自己的排空钩子，不复用核心包更新假设。

Cordis 可在未来真实需要进程内服务组合的管理端采用，但不能成为路由器联网前提。
插件开发和安装入口见[插件开发](../development/plugins.md)。

## 独立插件与热加载

独立插件安装到 `/usr/libexec/opl-netfleet/plugins/<id>/`，包含 `manifest.json` 和可执行
`control`。声明使用 `opl-netfleet-plugin.v1`，记录 ID、名称、版本、API major、软件包、
依赖、适用后端、权限类别及自定义动作的读写分类。代码路径由安装布局确定，浏览器不能
指定可执行文件或 shell 命令。`control` 可使用任何设备已安装的语言运行时。

每次清单读取重新发现插件，每次调用启动当前 `control`，没有常驻代码缓存。安装和替换
插件不要求重启核心。`get/load/unload` 是稳定生命周期动作，`reload` 由宿主顺序执行
unload、回读、load、回读。`get` 返回 `loaded` 与 `ready`；unload 必须先旁路、排空并清理
自身资源，再返回 loaded=false。load 失败时宿主尝试 unload 并回读，失败恢复未确认会明确
返回。只有显式 load/reload 启用插件，安装本身不接管流量。

`plugins-list` 只读取安装文件；`plugin-read` 只调用 get 或声明为 read 的动作；
`plugin-call` 执行生命周期或声明为 write 的动作。写请求需要确认及清单返回的 revision，
宿主在共享 mutation lock 内重新读取身份并验证；锁不传递给插件进程。revision 绑定 manifest 和入口字节，
插件自己的业务状态 revision 通过 params 交给其状态 owner 校验。RPC 的 read/write ACL
分别授权，插件声明不能扩大现有 ACL。所有插件请求和响应有大小上限、执行有时间上限，
失败不会把插件代码导入核心进程。list 不启动插件、不执行探测。

插件来自管理员信任的软件包来源，以设备管理员权限运行。manifest 权限用于审阅与接口
准入，不是 OS 沙箱；第三方代码的安装信任与普通 OpenWrt 软件包一致。固定目录必须由
root 持有、不可由其他用户写入，拒绝符号链接入口、越界标识和插件对内置模块名称的覆盖。

安装、升级与卸载使用标准 APK/IPK。软件包钩子在替换或删除旧代码前调用旧插件 unload
并确认排空；APK 不保证根据钩子失败阻止操作，所以钩子在未确认退出时持续等待，不返回
假成功。用户可先显式卸载运行实例，再操作软件包。升级后显式 load，新代码即时生效；
包钩子在 `/var/run/opl-netfleet-plugin-maintenance/<id>` 建立维护标记，并调用仅 root CLI
可用的 `plugin-drain`。宿主在同一锁内完成 unload/get 回读并写入 `replacing` 标记；排空
期间只允许 get/unload，进入 replacing 后禁止全部插件执行，直到包后置钩子清除标记，
避免替换字节期间调用插件。plugin-drain 重试在 replacing 阶段幂等成功。中断留下的标记需完成包
恢复并检查文件后再清除。插件状态保留在自身私有目录，状态迁移及回滚由插件负责。
涉及数据面的插件仍需 QEMU 和
独立授权设备验收；基础宿主通过并不等于所有第三方插件均可安全接管网络。

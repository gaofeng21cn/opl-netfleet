# 微内核与功能插件组合

本方案定义 NetFleet 进一步微内核化的方向。已实现的进程插件热加载、开发工具和安装
生命周期由[模块与扩展](../architecture/extensions.md)维护；本方案中的服务组合、依赖
就绪编排与内置功能迁移尚未成为当前接口。

## 目标与分工

借鉴 Cordis 的上下文、服务依赖和可销毁生命周期，NetFleet 内核只保留组合机制，网络
能力由插件提供。OpenWrt 继续采用适合设备的进程与服务模型；微内核理念不要求引入
Node.js 或将不同语言的实现放进同一个进程。

| 对象 | 责任 |
| --- | --- |
| 插件包 | 可校验、可安装的代码与资源；版本、来源、许可证和系统依赖 |
| 插件实例 | 配置、运行状态、生命周期及其独占资源；同一包可按真实需求扩展实例模型 |
| 服务合同 | 插件提供的具名能力、接口版本、调用与失败语义 |
| 系统配置 | 启用哪些插件、配置引用、必需能力及服务提供者绑定 |
| 内核 | 发现、版本与依赖解析、调用准入、生命周期协调、事件分发、事务及资源释放机制 |

订阅下载、地区识别、选择策略、配置编译、Mihomo 后端、DNS/透明代理、诊断、UI 投影和
恢复策略都可成为功能插件。没有哪项功能因为现在写在核心目录里就永久留在内核。
基本恢复机制与具体恢复策略分开：内核负责失败事务的退出和资源交还，策略插件决定
恢复到哪个可用配置或出口。

## 服务与依赖

插件声明提供和消费的服务及接口 major。系统配置明确选择提供者，不能通过目录顺序、
显示名称或“最后安装者”决定控制权。内核在加载前解析依赖图、检查版本与循环依赖，
按依赖关系启动，并在真实就绪后开放服务调用。包管理器解决安装依赖，内核解决运行
依赖；已安装不等于已就绪。

一个状态只有一个可写 owner。其他插件通过版本化服务读取或提交命令，不直接打开
对方私有文件。原有 policy、订阅、测量与激活事务沿现有合同迁移，不能在迁移中生成
第二份事实源。事件传递变化通知，读取服务取得当前事实；不能用漏收事件后的本地缓存
代替 owner 状态。跨进程事件需有明确的取消、丢失检测和重新读取路径。

网络接管、核心启停及恢复所需服务列为系统配置的必需依赖。缺失时停止新的激活事务，
仍保留正在使用的已验证路径及退出能力。保护来自依赖关系、资源管理和回读，而非把
业务实现固定编译进内核。

## 热替换与退出

热替换先检查候选接口、依赖与配置，再暂停新调用、排空旧实例并交还资源，随后切换到
新实例并回读。调用绑定实例 generation，旧调用不能跨代写入新状态。持久数据迁移由
插件实现，宿主协调迁移前置条件和失败回滚；不能仅以程序版本变化推断状态可兼容。

无状态诊断和资源插件可以直接复用现有卸载再加载。持有 TCP/SSE、DNS 或内核规则的
插件需提供业务特定的排空及接管机制；同一监听或流量 owner 的交接须逐项验证。
“无需重启宿主”与“所有既有连接无损转移”是不同合同，由各插件声明并提供证据。

## 沿真实调用链迁移

优先将依赖较少的诊断、资源管理接入独立插件，随后迁移订阅与测量服务，再迁移选择和
编译，最后交接核心及数据面的接管与恢复策略。每次只替换一个明确 owner，让实际
caller 经新服务完成同一用户操作后，再删除原有实现及注册，不长期保留两套 writer。

开发者继续使用统一脚手架、包布局、签名安装和组件页。服务接口由上述迁移中的真实
提供者与消费者共同确定，当前插件无需等待整个微内核改造完成即可开发和安装。

每个迁移单元需证明：现有功能仍可用、独立安装更新生效、依赖缺失与不兼容有明确结果、
热替换失败能够退出或恢复、核心与数据面状态可回读。数据面变化遵循现有 QEMU 和
独立授权设备验收边界。

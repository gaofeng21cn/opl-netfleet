# 微内核服务组合与显式绑定

## 上下文

NetFleet 的订阅、选择、编译、后端与管理能力需要独立开发、安装和替换。静态导入的
内置模块使功能版本绑定到核心发布，也让第三方只能增加外围能力。拆分代码必须保留
单一状态 owner，并能交接服务、监听和网络规则等长期资源。

## 决定

采用受 Cordis 上下文、服务依赖与生命周期理念启发的组合方式，在 OpenWrt 原生 UCode
运行环境中实现。微内核负责组合机制，业务实现以具名、版本化服务发布；系统配置显式
选择服务提供者，插件只通过已声明的依赖调用其他服务。自有与第三方插件共用协议。

每次调用使用独立上下文，代码租约使包更新等待在途调用结束。资源插件提供排空和恢复
方法，持久数据仍由原 owner 管理。进程插件与 UCode 服务并存，为其他语言提供同一
安装与管理入口。当前行为由[微内核合同](../architecture/microkernel.md)和
[扩展合同](../architecture/extensions.md)维护。

## 取舍

按调用创建上下文符合设备端 one-shot 命令和既有 procd 模型，不要求常驻 Node.js 宿主；
代价是每次调用需要解析与创建所需服务。显式绑定比目录扫描优先级多一份配置，但能
明确服务替换由谁决定，避免安装顺序改变运行 owner。

把全部业务保留在核心中、只开放外围插件，会限制独立替换；以私有文件路径互相导入
则无法形成稳定接口。另建常驻通用宿主会引入第二套运行与故障生命周期。以上路径都
无法同时满足设备运行模型、功能独立交付和单一状态 owner。

## 重审条件

当实测证明逐次上下文创建成为主要性能瓶颈，或真实功能需要跨调用共享的长期服务时，
重新评估实例缓存或常驻宿主。新增机制仍需明确代码代际、调用取消、资源交接和恢复
owner，不以插件数量本身作为引入条件。
